## 排查：app1.1 下载到板子后 OLED 不显示

### 结论（代码层面）
OLED 驱动本身不是原因。用 `md5sum` 比对确认：
`08-boot-ota/app1.1/Core/Src/oled.c` 与 `05-mqtt-freertos`/`06-canopen` 的 oled.c
**逐字节相同**（差异仅为删掉了 case 1 的 6x8 分支、OLED_ShowCN/DrawBMP/Test）。
`oled.h`、`i2c.c` 同样与第 5 章一致。main.c 中 OLED_Init/CLS/ShowStr 调用位置正确，
在 `INA226_Init()` 之前。故怀疑点转向「app1.1 根本没跑起来」。

### 关键事实（本次核实）
- boot 工程：IROM `0x08000000` / 0x2000，镜像 0x1730 字节，printf 走 **USART1 @115200**。
- app1.1：IROM `0x08002000` / 0x7000，镜像 0x6FE0 = 28640 字节，
  **只剩 32 字节余量**（Max 0x7000 = 28672）。`app1_1.hex` 起始记录
  `:020000040800F2` + `:10200000` 确认烧录地址为 0x08002000。
- app1.1 main() 第一句 `SCB->VTOR = FLASH_BASE | Application_1_Addr`
  = 0x08000000 | 0x08002000 = **0x08002000**。因此 app1.1 **不能**烧到 0x08000000 单独运行
  （`app1_1.bin` 是无地址裸文件，用 CubeProgrammer 按默认 0x08000000 烧会挂）。
- boot 的 `Start_BootLoader()`：读 `Application_2_Addr + Application_Size - 4`
  = **0x0800FFFC**。仅当值为 0xFFFFFFFF（正常）或 0xAAAAAAAA（升级）才跳转；
  其它值走 default → `printf("> Error:%X")` → **return，不跳转**。
  → 若该处残留旧 OTA 标志，bootloader 会把 app2 区垃圾拷进 app1，把 app1 冲掉。
- app1.1 用 **TIM1** 作 HAL 时基（`stm32f1xx_hal_timebase_tim.c`，TIM1_UP_IRQn），
  第 5/7 章同款；TIM1_UP_IRQHandler / TIM4_IRQHandler 在 stm32f1xx_it.c 中已实现。
- boot 的 `IAP_ExecuteApp()` 跳转前**没有关中断、没有停 TIM1 时基、没有 deinit**。
  bootloader 的 TIM1 一直在跑，跳转后到 app 写 VTOR 之前，若 TIM1_UP 中断到来，
  会去 0x08000000 取向量、执行 bootloader 的中断服务函数（其 htim1 所在 RAM 已被 app
  的 .data/.bss 覆盖）——经典 IAP 竞态，应作为健壮性修复项。

### 建议的排查顺序
1. 串口 USART1 @115200 看 bootloader 横幅。无输出 → boot 没跑/被擦。
2. 有横幅但 `> Error:XXXXXXXX` → 0x0800FFFC 残留脏标志。
3. 有 `> Normal start... > Start APP1...` 但 OLED 仍黑 → 查 app1 烧录地址、
   I2C 总线、boot→app 中断竞态。
4. 代码健壮性问题（非本次直接原因，但建议修）：
   - `WriteCmd/WriteDat` 完全忽略 `HAL_I2C_Master_Transmit` 返回值 → I2C 失败无感知。
   - `OLED_Init()` 上电只 `HAL_Delay(1)`，SSD1306 要求 VDD 稳定后 ~100ms。
   - `OLED_SetPos()` 第三句 `WriteCmd((x&0x0f)|0x01)`，低半字节 bit0 被强制置 1，
     每字符右移 1 列（第 5 章同款，属既有小瑕疵，非本次原因）。

## 追加：用户回图确认烧写地址

用户贴 Keil Options for Target → **Target** 页截图：IROM1 on-chip `0x8002000` / `0x7000`，
IRAM1 `0x20000000` / `0x5000`，Xtal 8MHz，ARM Compiler V5，Use MicroLIB。
→ 链接地址确认无误，与 map 一致，该假设排除。

**但必须区分两个不同设置（用户容易混淆）：**
- Target 页 IROM1 = 只决定**编译链接地址**。
- Options → **Utilities** → Settings → Download Function = 决定**烧写时擦除范围**
  （Erase Full Chip / Erase Sectors）。勾 Erase Full Chip 会把 0x08000000 的 bootloader
  一起擦掉 → app1.1 永远不被跳转 → OLED 黑屏。
- 已确认 `.uvprojx`/`.uvoptx` 里**不存** Erase 相关字段（grep -i "rase" 无结果），
  该设置由 IDE 全局配置管理，无法从工程文件判断，只能让用户在 GUI 里看。

另：Target 页设置只属于 app1.1 工程；bootloader 要在 **boot 工程**里烧
（它自己是 IROM `0x8000000` / `0x2000`）。在 app1.1 工程点 Download 不会写入 bootloader。

解 `app1_1.hex` 得到的向量表（供对照 Memory 窗口）：
```
:020000040800F2  → 扩展线性地址 0x0800
:10200000 18160020 01210008  → 0x08002000: SP=0x20001618, Reset=0x08002101
:04000005080020ED  → 入口 0x080020ED
```
镜像健康。对照检查：`0x08000000` 前 4 字节应为 0x2000xxxx（boot 栈顶），
`0x0800FFFC` 应为 0xFFFFFFFF。

## 根因确认 + 已修复（23:23）

用 STM32CubeProgrammer CLI 直读芯片 Flash，一锤定音：

```
0x08000000 : FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFF   <- 空的！bootloader 从没烧进去
0x08002000 : 20001618 08002101 08006A79 08005987   <- app1.1 烧对了
0x0800FFFC : FFFFFFFF                              <- 启动标志正常
```

芯片识别正常（Device ID 0x410，STM32F103 Medium-density，Flash 64KB，3.24V），
所以不是硬件/连接问题。

**根因：`0x08000000` 是空片。** app1.1 的 IROM 在 0x08002000、main() 又把 VTOR 设成
0x08002000，所以没有 bootloader 就没人跳转过去；CPU 从 0x08000000 取到 0xFFFFFFFF →
HardFault → OLED 全黑。这同时解释了 Keil 调试时
`error 122: AGDI: memory read failed (0xFFFFFFFE)`：调试器读复位向量得到 0xFFFFFFFF，
`&~1` 就是 0xFFFFFFFE。

**修复动作（已执行）：**
1. 先备份整片 Flash 到 `.workbuddy-ai/backup/flash-before-bootloader-20261015.bin`（64KB）。
2. `STM32_Programmer_CLI -c port=SWD mode=normal -w boot/MDK-ARM/boot/boot.hex -v`
   → `Erasing internal memory sectors [0 5]`，只擦 0x08000000–0x080017FF，
     **app1.1 的扇区没动**；`Download verified successfully`。
3. 回读确认：0x08000000 = `20000880 08000109`（boot 向量表有效），
   0x08002000 仍是 `20001618 08002101`（app1.1 完好），0x0800FFFC 仍 `FFFFFFFF`。已 `-rst` 复位。
