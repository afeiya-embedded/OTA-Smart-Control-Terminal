## 分析 07-canopen-freertos 工程结构 + 生成面试题库

**工程性质**：STM32F103C8T6 多协议工业控制终端（OTA-Smart-Control-Terminal 系列第 7 个示例）
- CubeMX 6.14.1 + HAL F1 V1.8.6 + Keil MDK V5.32
- FreeRTOS V10.3.1（CMSIS-OS v1 封装），3 个任务：ModbusTask / MQTTTask / CANopenTask，均 osPriorityNormal，栈 128 words
- 三大协议栈：CanFestival(CANopen 从站) / FreeModbus(RTU 从机) / MQTT(经 ESP8266 或 ML307 的 AT 指令)
- 共享数据中枢：`REG_HOLD_BUF[]`（Modbus 保持寄存器），被三协议共同读写

**关键机制（已核实）**
- TIM1 = HAL 时基 1ms，同时软计数 500ms 置 `TIM1_Timeout_Flag`
- TIM2 = CanFestival 时基，PSC=72-1 → 1us 计数，ARR=0x2000；`setTimer` 直接改 `TIM2->ARR`
- TIM4 = 10ms 单次，做模组串口「一帧接收结束」判帧
- CAN：PSC=8, BS1=6TQ, BS2=2TQ → 500kbps，采样点 77.8%；滤波器 Mask 全 0 收全部
- 中断优先级全部 = 5（= configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY），NVIC_PRIORITYGROUP_4
- 串口收包：IDLE 空闲中断 + DMA_CIRCULAR + 半满/全满回调 + QUART3 环形队列
- OD 自定义区 0x2000 子索引 01~0A 映射 Control/TP/RH/VL/CU/PW/VR/CPU/RES/SlaveAddress

**发现的代码隐患（面试可主动提）**
1. ISR 里 `printf`（fputc = HAL_MAX_DELAY 阻塞发送）— 最高危
2. `REG_HOLD_BUF` 三任务/中断共享，无任何锁
3. `uint8_t Length = DMA_BUF_SIZE(256) - counter` 溢出风险
4. 任务栈 512B 偏小；`configTOTAL_HEAP_SIZE` 仅 3072
5. 任务里用 `HAL_Delay` 忙等（AT 超时最长 200s）
6. CAN 中断里直接 `canDispatch()`；`AutoBusOff/AutoRetransmission = DISABLE`
7. `huart->ErrorCode &= HAL_UART_ERROR_FE` 应为 `&= ~`
8. `canSend` 里 `while` 当 `if` 用
9. HardFault_Handler 无信息
10. TIM3 初始化后未使用

## MQTT 下行命令延时链路分析

用户反馈「MQTT 下行命令到硬件有延迟」，逐段核算（100 字节帧 / 115200 / F103）：

| 环节 | 耗时 | 性质 |
|---|---|---|
| 网络（Broker→模组） | 30~300ms | 不可控 |
| USART3 DMA 接收 | 帧长 × 86.8us ≈ 8.7ms | 波特率决定 |
| **TIM4 判帧等待** | **固定 10ms** | 可优化 |
| **逐字节转发到 USART1** | **≈ 8.7ms 阻塞** | 可优化，最大代码隐患 |
| cJSON 解析 | ≈ 2ms | 正常 |
| **等 ModbusTask 轮询** | **平均 5ms / 最坏 10ms** | 可优化 |
| GPIO 动作 | < 0.1ms | 正常 |

MCU 内部合计 ≈ 35ms。

**三个瓶颈的根因**
1. **逐字节转发**：`WIFI4G_Parse_Queue()` 里 `while` 循环中每出队 1 字节就调一次 `HAL_UART_Transmit(&huart1, RecvBuf+i, 1, 1000)`，N 次阻塞调用。且该函数运行在 **TIM4 中断上下文**（main.c 的 `HAL_TIM_PeriodElapsedCallback`）。
2. **TIM4 判帧 10ms**：TIM4 PSC=7200-1→10kHz，ARR=100→10ms。而 115200 下 3.5 字符仅 ≈300us，余量过大。
3. **解析与执行解耦**：JSON 解析在中断里写 `REG_HOLD_BUF[0]`，但 GPIO 落地在 `Modbus_Parse()` 里，靠 ModbusTask 每 10ms 轮询触发。

**优化方案（按收益排序）**
1. TIM4 中断里只置标志，把 `WIFI4G_Parse_Queue()` 移到 MQTTTask 上下文执行
2. 去掉逐字节转发（先全部出队再一次性发，或删除该调试转发）
3. TIM4 判帧窗口 10ms → 2ms（改 ARR=20）
4. 抽出 `Apply_ControlWord()`，在 JSON 解析完成后立即调用，省掉等轮询的 5~10ms
5. 注意：`HAL_UART_Transmit` 依赖 `uwTick` 超时，而 TIM4(prio 5) 高于 TIM1(prio 15)，在 TIM4 中断里 `uwTick` 不递增 → 超时保护实际失效

**测量方法**：用空闲 GPIO 打点（收到 `{` 拉高、`LED_Control` 拉低）+ 逻辑分析仪；或用 `TIM2->CNT`（1us 精度）分段打时间戳。

## 补充：为什么 Modbus 命令快、MQTT 慢（根因定位）

**关键发现**：`ModbusTask` 的循环是
```c
for(;;) { eMBPoll(); Modbus_Parse(); osDelay(10); }
```
`eMBPoll()` 处理帧 → `eMBRegHoldingCB()`（FreeModbus/port.c:64）写 `REG_HOLD_BUF[0]`，
**紧接着下一行 `Modbus_Parse()` 就读到并驱动 GPIO**——间隔仅几微秒。

而 MQTT 的写入发生在 **TIM4 中断**里，与 `Modbus_Parse()` 之间隔着 `osDelay(10)`，平均等 5ms / 最坏 10ms。

**结论**：Modbus 快不是优化出来的，是「写入者与执行者恰好是同一循环里相邻的两行代码」这个巧合。
`Modbus_Parse()` 实际兼任了**全局 GPIO 执行器**，刷新周期被绑死在 10ms——任何其它协议（MQTT / CANopen）写控制字都要忍受这个等待。

**补充事实**
- Modbus 挂在 **USART2**，RXNE 逐字节中断 + T3.5 定时器判帧，**不走 DMA**
- `REG_HOLD_BUF[]` 被三处引用：Modbus 保持寄存器、MQTT JSON、CANopen OD 0x2000（TestSlave.c:566-574）
- `Modbus_Parse()` 一个函数干三件事：500ms 传感器刷新、从机地址修改、10ms GPIO 落地 —— 职责混杂

**Modbus 侧最坏 ≈ 11ms（无网络）；MQTT 侧 MCU 内 ≈ 31ms + 网络 30~300ms。**
