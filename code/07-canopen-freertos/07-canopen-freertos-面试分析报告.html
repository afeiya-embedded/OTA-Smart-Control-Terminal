1一句话讲清这个工程

这是一台工业智能控制终端：通过 I2C/ADC 采集温湿度（AHT20）、电压电流功率（INA226）、电位器与芯片温度， 统一汇聚到一块共享的「保持寄存器」REG_HOLD_BUF[]；再同时用 三条通道对外提供服务与上报——

  • Modbus RTU 从机（RS485）：上位机/PLC 读写寄存器，实现本地组态与远程控制；
  • MQTT over WiFi/4G：经 ESP8266 或 ML307 模组用 AT 指令连云，周期上报 JSON 遥测、订阅下行 JSON 控制指令；
  • CANopen 从站（CAN 总线）：实现 NMT/SDO/PDO/心跳，把同一批数据发布到工业 CAN 网络。

控制输出为 LED1/LED2、蜂鸣器、继电器，另有 OLED 本地显示与 6 个按键交互。三个协议共用同一份数据，做到「一次采集，三网可达」。

面试时的电梯陈述（30 秒版） 这是一个基于 STM32F103 的多协议工业终端。我用 CubeMX 搭 HAL 层，移植 FreeRTOS 跑三个同优先级任务分别承载 Modbus RTU 从机、MQTT 云端通信和 CANopen 从站；数据用一块共享寄存器做中枢，三个协议读写同一份数据。外设侧做了 UART 空闲中断 + DMA 循环双缓冲收包、环形队列缓存、TIM2 给 CanFestival 提供 1us 时基、TIM4 做模组数据包超时判帧。

3面试题库（按模块 · 含答题要点）

标记说明：必问 高频核心题，重点 大概率会问， 基础 查漏补缺，加分 答好能拉开差距。

A · C 语言与嵌入式基本功

A1volatile 是干什么的？工程里 __IO uint8_t WIFI4G_CMD_Status 为什么必须加？必问

要点：告诉编译器该变量可能被「编译器看不见的力量」改变，禁止把它缓存在寄存器里，每次访问都从内存重新读。本工程场景：WIFI4G_CMD_Status 在 USART3 中断里被改写，在任务里的 Test_WIFI4G_CMD_Status() 忙等循环中读取。若不加 volatile，-O2 下编译器会认为循环里没人改它，直接优化成死循环。同理：TIM1_Timeout_Flag、Modify_SlaveAddress_Flag、MQTT_Download_Flag。注意 __IO 就是 volatile 的 CMSIS 别名。

A2static 修饰局部变量 / 全局变量 / 函数分别有什么效果？重点

要点：①修饰局部变量 → 存储期变为整个程序，放 .data/.bss 而非栈，只初始化一次；②修饰全局变量/函数 → 链接属性变 internal，只在本编译单元可见，避免重名；③修饰函数 → 内部链接。本工程例子：Get_CPUID() 里 static uint8_t cpuid[32]——返回的是局部数组地址，不加 static 返回的就是悬空指针，函数一返回栈就失效了。这是必答的经典点。

A3结构体字节对齐？为什么 CAN 报文处理要小心对齐？重点

要点：默认按成员中最大对齐数补齐，会插入 padding。踩坑场景：把收到的字节流直接 memcpy 到结构体、或按结构体解析网络/总线数据，会因 padding 错位。解法：#pragma pack(1) 或手动逐字段移位拼装。本工程 Message 结构体（CanFestival）是逐字段赋值的，安全；但你可以主动提一句「如果做协议解析我会显式 pack 或手拼」。

A4大小端？CanFestival 里的 CANOPEN_LITTLE_ENDIAN 有什么用？重点

要点：小端 = 低字节存低地址。Cortex-M3 默认小端。CANopen 的坑：CANopen 报文在总线上按「小端」传输（低字节先发），但 SDO/PDO 的数值又是「高字节先发」的场景会混淆。CANOPEN_LITTLE_ENDIAN 宏控制 canDispatch/objacces 里的字节序转换（swapByte）。面试可延伸：网络字节序是大端，所以 Modbus 寄存器、TCP/IP 都要转。

A5memcpy / strcpy / sprintf 的区别与风险？基础

要点：memcpy 按字节复制、需显式长度、不认 \0；strcpy 遇 \0 停、不检查目标缓冲区大小 → 栈溢出风险；sprintf 会格式化并补 \0，同样不检查长度。本工程隐患：MQTT_SendData() 里 sendbuf[128] 拼 7 个整数的 JSON，若数值变大可能溢出；生产代码应改用 snprintf 并检查返回值。这个回答能直接显示你有代码安全意识。

A6REG_HOLD_BUF[0] = REG_HOLD_BUF[0] & (~LED1_CMD) 是怎么实现位操作的？基础

要点：用「按位与取反」清位、「按位或」置位。LED1_CMD = (1<<0)、LED2_CMD=(1<<1)、BEEP_CMD=(1<<2)、RELAY_CMD=(1<<3)，一个字节低 4 位分别对应 4 个执行器。写 0 用 &= ~mask，写 1 用 |= mask。可延伸：读改写非原子，多任务/中断并发时会丢更新。

A7内存分区？20KB SRAM 怎么规划？重点

要点：栈(Stack) / 堆(Heap) / .bss(未初始化全局) / .data(已初始化全局) / .rodata(常量) / .text(代码，在 Flash)。本工程粗算：FreeRTOS 堆 3072B + Idle 静态栈 512B + 3 个任务栈各 512B + RX1_Buf/RX3_Buf 各 256B + QUART3 队列 256B+8B + RecvBuf[256] + OLED 显存 + 各种缓冲，20KB 相当紧张。startup 里 Stack_Size 0x400 / Heap_Size 0x200 也要提。

B · STM32 / HAL / 外设

B1讲一下时钟树：为什么 APB1 是 36MHz，定时器却是 72MHz？必问

要点：HSE 8MHz → PLL ×9 → SYSCLK 72MHz → AHB 不分频 72MHz → APB1 2 分频 = 36MHz，APB2 不分频 = 72MHz。关键规则：当 APB 分频系数 ≠ 1 时，挂在该总线上的定时器时钟 = APB 时钟 × 2，所以 APB1 定时器实际 72MHz。CAN 挂 APB1，时钟 36MHz，这也是 500kbps 计算的基准。

B2HAL_Delay() 的实现原理？为什么这里把时基从 SysTick 换成了 TIM1？必问

要点：HAL_Delay 本质是拿 uwTick 做非阻塞比较忙等，而 uwTick 由时基中断里的 HAL_IncTick() 累加。换 TIM1 的原因：FreeRTOS 要独占 SysTick 做任务调度（xPortSysTickHandler），如果 HAL 也用 SysTick，两者会打架、HAL_Delay 在调度器挂起时不准。所以 CubeMX 里把 SYS Timebase Source 改成 TIM1，并单独在 stm32f1xx_hal_timebase_tim.c 里实现 HAL_InitTick。这是 CubeMX + FreeRTOS 组合的标配考点。

B3CAN 波特率是怎么算出来的？采样点为什么重要？必问

要点：见 2.4 表。36MHz ÷ Prescaler(8) = 4.5MHz = 1 TQ；1 位 = Sync(1) + BS1(6) + BS2(2) = 9 TQ；4.5MHz ÷ 9 = 500kbps。采样点 = (1+BS1)/总TQ = 7/9 ≈ 77.8%。为什么要采样点：采样点太靠前抗抖动差、太靠后同步余量不足，CiA 301 建议 75%~87.5%。SJW=1TQ 表示允许重同步补偿 1 个 TQ。

B4AT24C02 用 I2C 怎么读写？HAL_I2C_Mem_Write 里的参数什么意思？重点

要点：AT24C02 是 2Kbit=256 字节 EEPROM，8 位字地址。HAL_I2C_Mem_Write(&hi2c1, DevAddr, MemAddr, I2C_MEMADD_SIZE_8BIT, &data, 1, timeout)：设备地址(0xA0写/0xA1读)、内存地址(0)、地址长度(8位)、数据、长度、超时。本工程用法：从机地址存在 EEPROM 偏移 0，上电 Read_SlaveAddress() 读回；读到 0 或 0xFF 视为未烧录，兜底为 1。注意点：EEPROM 写周期 5ms，所以写完后 HAL_Delay(10) 再重初始化。

B5ADC 怎么测 CPU 温度和电位器？基础

要点：F103 内部温度传感器接在 ADC1_IN16，需先使能 TSVREFE；电位器接 ADC1_IN1（PA1）。采样时间 239.5 周期是为了高阻源稳定。温度换算：T(℃) = (Vsense - V25) / Avg_Slope + 25，F103 典型 V25≈1.43V、斜率≈4.3mV/℃。

C · 中断 / NVIC / 通信收包

C1为什么所有外设中断优先级都设成 5？和 FreeRTOS 有什么关系？必问

要点：见 2.2。configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5 → 数值 < 5 的中断不受 FreeRTOS 临界区屏蔽，绝不能在里调 FromISR API；数值 ≥ 5 的中断会被 portENTER_CRITICAL 屏蔽，可以安全调用。设为 5 是「能调用 RTOS API 的最强优先级」。反问加分点：可以指出 SysTick 和 PendSV 必须是最低优先级 15，否则上下文切换会被打断。

C2串口「空闲中断 + DMA」是怎么工作的？比纯中断好在哪？必问

要点：DMA 配成 DMA_CIRCULAR 循环模式，一直把 RX 数据搬到 RX3_Buf[256]，CPU 全程不参与；总线空闲一个字节时间后触发 IDLE 中断，此时 DMA_BUF_SIZE - __HAL_DMA_GET_COUNTER() 就是本帧长度，取出即可。优势：①不定长帧自适应，不需要事先知道长度；②CPU 占用极低，适合 115200 甚至更高速率；③不会像「逐字节中断」那样丢字节。配套：还有 RxHalfCplt（半满）和 RxCplt（全满）回调，用 RX3_Offset 记录已处理位置，防止循环覆盖。这是本工程最值得讲的技术亮点之一。

C3为什么还要用 TIM4 延时 10ms 才去解析？重点

要点：这是「软件判帧」：模组（尤其早期 ESP8266）回显可能被拆成多次 IDLE 中断，或者一条 AT 响应分几段到达。做法是每次收到数据就重启 TIM4（10ms 单次），如果在 10ms 内又有新数据就重置，直到总线安静 10ms 才认为「一包收完」，关掉 TIM4 再统一解析队列。本质是「以静默间隔判帧尾」，和 Modbus RTU 的 3.5 字符间隔判帧是同一个思想，可以联系起来讲。

C4工程里在中断中调用 printf / HAL_UART_Transmit，有什么问题？必问

要点：这是本工程真实存在的隐患，面试官很可能会指出来。fputc 重定向成阻塞式 HAL_UART_Transmit(..., HAL_MAX_DELAY)，在 USER_UART_IRQHandler 里 printf("FIFO Full\n") 会：①以 115200 波特率阻塞几毫秒；②HAL_UART_Transmit 内部依赖 uwTick 超时，若中断优先级高于时基中断会死等；③破坏中断的「快进快出」原则，拖垮整个系统实时性。正确做法：中断里只置标志/入队，把打印放到任务里；或用无阻塞的 DMA 发送；至少改成环形缓冲 + DMA。

C5按键 EXTI 去抖怎么做的？这种实现有什么优缺点？重点

要点：在 HAL_GPIO_EXTI_Callback 里用全局 uwTick 与 old_uwTick 做差，小于 200ms 直接 return，否则更新时间戳并处理。优点：实现简单，无需额外定时器。缺点：①uwTick 在中断里读、在主循环写，未加原子保护，uwTick - old_uwTick 是 32 位运算在 M3 上本身原子，问题不大，但语义上应加 volatile；②去抖窗口 200ms 偏大，快速连按会丢键；③在 ISR 里调 printf 和 LED_Control，同样有 C4 的问题；④Key_Value 是「单变量事件队列」，连续两次按键会覆盖。

C6串口错误恢复为什么只清 FE/NE？huart->ErrorCode &= HAL_UART_ERROR_FE; 这行对吗？加分

要点：清 FE（帧错误）/NE（噪声错误）后 HAL_UART_DMAStop + 重新 HAL_UART_Receive_DMA，是应对 ESP8266 上电时波特率不对导致的乱码流——这个场景抓得很准。但 &= 是「保留该位」而不是「清除」，写成 ErrorCode &= HAL_UART_ERROR_FE 逻辑上是保留 FE 位、清掉其它位，与注释「清除错误标志位」不符，正确应为 &= ~HAL_UART_ERROR_FE。能主动指出这个笔误，是很强的加分项。

D · DMA

D1循环模式 vs 普通模式？为什么这里必须用循环模式？重点

要点：普通模式传完就停、需要软件重启；循环模式搬完自动回到起点继续，永不停止，适合「持续接收」的场景。本工程串口收包是永续的，所以 DMA_CIRCULAR。

D2怎么知道已经收了多少字节？为什么用 RX1_Offset 这个偏移量？必问

要点：NDTR（剩余传输数）递减，所以已收 = BUFFER_SIZE - __HAL_DMA_GET_COUNTER()。为什么要有 Offset：因为缓冲区是循环的，处理过一半后不能重复处理，RX_Offset 记录「上次读到哪」，本次长度 = 总已收 - 已处理偏移。当 DMA 绕回（半满/全满中断）时把 Offset 归零。

D3uint8_t Length = DMA_BUF_SIZE - __HAL_DMA_GET_COUNTER(...)，DMA_BUF_SIZE=256，有问题吗？加分

要点：有。Length 是 uint8_t（0~255），而 DMA_BUF_SIZE=256，当 DMA 计数值为 0 时结果 256 会截断成 0；同理 RX1_Offset/RX3_Offset 也是 uint8_t，理论上可到 255 但语义上应能表示 256。修法：把类型改成 uint16_t/uint32_t。这是「类型宽度不足」的典型题，能主动发现非常加分。

E · FreeRTOS

E1osThreadDef(Modbus, ModbusTask, osPriorityNormal, 0, 128) 里的 128 是什么单位？栈够吗？必问

要点：128 是 StackType_t 个数，Cortex-M3 上 1 word = 4 字节，即 512 字节。风险：任务里有 sprintf、cJSON_Parse、递归解析，512B 非常容易栈溢出。生产建议 ≥1KB，并打开 configCHECK_FOR_STACK_OVERFLOW + vApplicationStackOverflowHook。回答时主动提这个改进点，面试官会觉得你真跑过。

E2三个任务同优先级，会发生什么？重点

要点：同优先级任务在 configUSE_TIME_SLICING（默认 1）下按时间片轮转（每 tick = 1ms 切换），本质是「分时共享」而非抢占。好处是简单；坏处是实时性无法分级。更合理的设计：CANopen 收报文要求快，应给较高优先级；Modbus 轮询次之；MQTT 上报可以最低，或干脆用事件/信号量驱动而不是定周期死等。

E3configTOTAL_HEAP_SIZE = 3072，够不够？为什么？加分

要点：3 个任务 × 512B 栈 = 1536B，加 3 个 TCB（各约 90~100B）≈ 300B，合计约 1.9KB，剩 ~1.1KB 给内核队列/信号量。结论：能跑但余量很小，一旦某任务栈需求上升或再加任务就会 pvPortMalloc 返回 NULL，任务创建静默失败。可选方案：加大堆、改用 heap_4 并留意碎片、或全面改静态分配（本工程已开 configSUPPORT_STATIC_ALLOCATION）。

E4HAL_Delay 和 osDelay 有什么区别？在任务里用 HAL_Delay 会怎样？必问

要点：HAL_Delay 是纯忙等（CPU 空转，不释放 CPU），osDelay 会把任务挂起、让出 CPU 给别的任务。本工程隐患：MQTT_Connect_Server() → ESP8266_Connect_WIFI() → Test_WIFI4G_CMD_Status() 内部用 HAL_Delay(1) 死等，超时可达 200 秒！这会让 MQTTTask 占着 CPU 空转，如果它优先级最高会饿死其它任务。应改成 osDelay(1)。

E5REG_HOLD_BUF 被 3 个任务 + 多个中断同时读写，需要保护吗？必问

要点：需要。当前完全没有保护，是典型的「共享数据竞态」。风险场景：①MQTT 任务读 7 个寄存器拼 JSON 时，Modbus 任务刚好在写，会读到「半新半旧」的数据；②REG_HOLD_BUF[0] &= ~mask 是读-改-写三步，中间被抢占会丢更新。方案：短临界区用 taskENTER_CRITICAL；或加互斥量（注意中断里不能用 mutex，要用 FromISR 版本或关中断）；更好的做法是「双缓冲 + 原子指针交换」。

E6FreeRTOS 的启动流程是什么？SVC/PendSV/SysTick 分别干嘛？重点

要点：MX_FREERTOS_Init() 创建任务 → osKernelStart() → 配置 SysTick → SVC 异常启动第一个任务。三兄弟：SVC = 启动调度器/首次切任务；PendSV = 上下文切换（最低优先级，保证不打断其它中断）；SysTick = 每 1ms 产生 tick，判断是否要切任务。

E7工程为什么没开 FreeRTOS 软件定时器？CANopen 的定时怎么办？加分

要点：configUSE_TIMERS 未定义（默认 0），所以没有 Timer Task，省了 1 个任务的开销和内存。CANopen 需要的毫秒级定时由 硬件 TIM2 提供：setTimer() 直接改 TIM2->ARR，getElapsedTime() 读 TIM2->CNT，TIM2 中断里调 TimeDispatch() 驱动心跳/PDO 超时。好处：精度 1us、不依赖 RTOS、不受任务调度影响；坏处：耦合了硬件，移植时要改。这是「RTOS 定时 vs 硬件定时」很好的讨论素材。

F · CAN / CANopen（本工程核心，必被深挖）

F1CAN 总线的仲裁机制？为什么 CAN 适合工业现场？必问

要点：CAN 用「非破坏性逐位仲裁」：显性位(0) 覆盖隐性位(1)，节点边发边听，发现 ID 被压就退出、变成接收方，赢了的一方继续发，报文不丢失、不重发。ID 越小优先级越高。适合工业的原因：差分双绞线抗干扰、带 CRC-15 校验、自动重发、错误节点可自动退出（总线关闭），多主结构。

F2CAN 的 5 种错误检测机制？错误计数器怎么工作？重点

要点：位错误、位填充错误、CRC 错误、格式错误、应答错误。发送错误计数 TEC、接收错误计数 REC；TEC/REC > 127 进「错误被动」，TEC > 255 进「总线关闭(Bus-Off)」，自动脱离总线。本工程注意：AutoBusOff = DISABLE，意味着 Bus-Off 后不会自动恢复，必须软件干预；AutoRetransmission = DISABLE 则失败不自动重发。这两项在生产环境一般都要 ENABLE，是很好的「改进点」回答。

F3CANopen 的通信对象有哪些？必问

要点：

F4NMT 状态机是怎样的？本工程 setState(Initialisation) 后直接 setState(Operational) 对吗？必问

要点：标准状态机是 Initialisation → Pre-operational → Operational → Stopped 四态。各态能力：Init 只做自举和 OD 默认值加载；Pre-op 允许 SDO、NMT、心跳，但不允许 PDO；Operational 才允许 PDO 收发；Stopped 只留心跳和 NMT。本工程写法分析：CanFestival 的 setState(Operational) 内部会依次走 Init→Pre-op→Operational，所以功能上能跑通；但从「工程规范」角度，跳过显式的 Pre-op 阶段意味着放弃了在 Pre-op 里通过 SDO 动态配置 PDO 映射的机会——本工程 PDO 映射是 OD 里写死的，所以没问题。面试时把这两层讲清楚，就是高分答案。

F5对象字典是什么？0x1000 / 0x1017 / 0x1018 / 0x1400 / 0x1800 / 0x2000 分别是什么？必问

要点：对象字典是 CANopen 节点的「数据模型」，用 16 位索引 + 8 位子索引寻址，每个条目有数据类型和读写权限（RO/RW/WO）。

F6SDO 和 PDO 的区别？必问

要点：SDO 是「有应答的配置通道」，点对点、可靠、可传任意长度（加速 SDO ≤4 字节 / 分段 / 块传输），用于读写对象字典；PDO 是「无应答的实时通道」，广播式、一对一或一对多、最多 8 字节，用于过程数据。一句话记忆：SDO 配参数，PDO 传数据。PDO 又分事件触发、定时触发、SYNC 同步触发。

F7PDO 映射是怎么实现的？为什么要映射？重点

要点：在 0x1600（RPDO 映射）/0x1A00（TPDO 映射）里填「索引+子索引+位长」，把多个 OD 变量打包进一帧 PDO，一帧最多 8 字节。好处是用一帧传多个数据、效率高。本工程 PDO 映射在 TestSlave.od 里由 objdictedit 生成，运行时不再动态改。

F8CanFestival 是怎么移植到 STM32 的？setTimer / getElapsedTime 为什么这么写？必问

要点：CanFestival 是「协议栈与硬件解耦」的架构，需要用户实现 4 个移植接口： 

canSend()          // 发一帧，映射到 HAL_CAN_AddTxMessage
canDispatch()      // 收一帧，在 CAN RX 中断回调里调用
setTimer(value)    // 设定下次定时：TIM2->ARR = TIM2->CNT + value
getElapsedTime()   // 读当前时间：return TIM2->CNT
为什么这样写：TIM2 预分频 72-1 → 计数频率 1MHz → 1 个计数 = 1us，正好满足 MS_TO_TIMEVAL(ms) = ms*1000（见 timerscfg.h）。ARR 直接赋值实现「从现在起 value 微秒后到期」，中断里 TimeDispatch() 处理到期的定时任务。TIMEVAL_MAX = 0x2000 对应 TIM2 的 Period，防止超范围。这是「1us 精度的软件定时器」实现思路，很值得展开讲。

F9在 CAN 接收中断里直接调 canDispatch() 有什么风险？加分

要点：①协议栈处理可能耗时（SDO 分段、PDO 映射写入），在 ISR 里做会拉长中断、影响实时性；②canDispatch 内部可能反向调用 canSend（如 SDO 应答），在中断上下文里调 HAL_CAN_AddTxMessage 要保证邮箱可用，本工程 canSend 失败直接 return 0 不重试，会丢应答；③协议栈用了全局状态，中断与任务若并发访问同一 CO_Data 就有竞态。更稳的做法：ISR 里只把报文压入环形队列，用信号量唤醒 CANopen 任务在任务上下文里 dispatch。

F10看一下 canSend 里这段：while((HAL_CAN_AddTxMessage(...) != HAL_OK)) { return 0; }，有问题吗？加分

要点：有。这个 while 循环体内是无条件 return 0，所以循环最多执行一次——它实际上是 if，写 while 是误导。要么改成 if，要么真的实现「等邮箱空闲再重试」。另外 memcpy(TxMessage.Data, ...) 里 TxMessage 是未初始化的局部结构体，只用了它的 Data 成员，其余字段未赋值即传给 HAL_CAN_AddTxMessage（实际只读 Data），逻辑上碰巧没问题但属于「未初始化内存」的坏味道。能指出这两点，说明你审过代码。

G · Modbus

G1Modbus RTU 帧结构？为什么帧之间要 3.5 字符静默？必问

要点：帧 = 从机地址(1B) + 功能码(1B) + 数据(N) + CRC16(2B)。RTU 靠「时间间隔」判帧：帧内字符间隔 ≤1.5 字符时间，帧间 ≥3.5 字符时间；<1.5 字符时间的小停顿会被当作噪声丢弃。115200 波特率下 1 字符 ≈ 86.8us，3.5 字符 ≈ 304us。本工程关联：TIM4 的 10ms 判帧思想一致。

G2eMBInit / eMBEnable / eMBPoll 的关系？eMBPoll 是阻塞的吗？必问

要点：eMBInit(MB_RTU, 从机地址, 端口, 波特率, 校验) 配置模式与回调表；eMBEnable() 置状态为 ENABLED 并开接收；eMBPoll() 是非阻塞轮询：检查状态机是否有完整帧 → 校验 CRC → 分派到功能码处理 → 组织应答发出。所以必须放在任务循环里周期性调用，本工程每 10ms 一次。移植层需要实现 mbportserial.c / mbporttimer.c（定时器用于 3.5 字符超时）。

G3为什么改从机地址要 eMBDisable → eMBClose → eMBInit 走一遍？重点

要点：FreeModbus 的从机地址在 eMBInit 时被写入内部状态，运行中不能直接改，必须停掉协议栈、关闭串口、用新地址重新初始化。本工程流程：检测 Modify_SlaveAddress_Flag → 读 REG_HOLD_BUF[9]` 新地址 → 写 EEPROM → 停栈重启 → 同步 setNodeId() 给 CANopen。亮点：Modbus 地址和 CANopen NodeID 联动，这个设计可以主动讲。

G4支持哪些功能码？RS485 半双工怎么控制收发方向？重点

要点：本工程 mbconfig.h 全开：01/02 读线圈与离散输入、03/04 读保持/输入寄存器、05/06 写单个线圈/寄存器、0F/10 写多个线圈/寄存器、11 报从机 ID、08 诊断。RS485 半双工靠 RS485_WR（PB2）切换 DE/RE：发送前置高，发完（TC 标志）拉低。要提「必须在最后一个字节完全移出后才切回接收，否则会截断尾字节」。

H · 通信 / AT 指令 / MQTT

H1MQTT 的核心概念？QoS 0/1/2 的区别？必问

要点：发布/订阅模型，中间是 Broker，主题 Topic 分级（/ 分隔），支持通配符 +（单层）#（多层）。QoS0 最多一次（可能丢）、QoS1 至少一次（可能重复）、QoS2 恰好一次（开销最大）。还有遗嘱消息(LWT)、保留消息(Retained)、Clean Session。本工程：上行 STM32/UpLoad/<CPUID>、下行 STM32/DownLoad/<CPUID>，用 96 位芯片唯一 ID 做主题后缀和 ClientID，保证多设备不撞。

H2AT 指令交互框架是怎么设计的？重点

要点：三步走：①strcpy(Parse_Substr, "OK\r\n") 设定「期望匹配的应答特征串」；②清 WIFI4G_CMD_Status 标志；③HAL_UART_Transmit 发指令；④Test_WIFI4G_CMD_Status(timeout) 带超时忙等标志位。中断侧在 IDLE 中断把数据入队并启动 TIM4，TIM4 到点后 WIFI4G_Parse_Queue() 出队拼成 RecvBuf，strstr 匹配期望串 → 置 OK/ERROR 标志。优点：解耦清晰；缺点：超时用 HAL_Delay(1) 忙等，应改 osDelay；Parse_Substr 是全局共享的，多指令并发会串味。

H3为什么用环形队列缓冲模组数据？直接用数组不行吗？重点

要点：中断产生的速度和处理速度不匹配，队列起「削峰」作用，防止中断里处理不过来丢数据。本工程实现细节：sequeue_t 用「front/rear 相等为空、rear+1==front 为满」来区分空满，故意浪费一个元素。可以反问的点：队列本身没加锁，中断里 Enqueue_Bytes、任务里 Dequeue，front/rear 是 int32_t，单核 M3 上读写是原子的，但「判空→读→改 front」三步不是原子的，理论上存在竞态窗口，严格做法是临界区保护。

H4ESP8266 和 ML307 两套代码怎么切换的？基础

要点：用 #if MQTT_WIFI_4G_ENABLE 条件编译，ESP8266 走 AT+CWMODE/CWJAP/MQTTUSERCFG/MQTTCONN/MQTTSUB，ML307（4G）走 AT+DTUTASK/MQTT/MQTTIP/MQSUB/MQPUB。评价：用宏切换是入门做法，模块多了会代码膨胀；更好的设计是「抽象出统一的模组接口（函数指针表）」，运行时选择驱动，符合开闭原则。

H5cJSON 解析时要注意什么？重点

要点：①cJSON_Parse 失败返回 NULL 必须判空；②cJSON_GetObjectItem 也可能返回 NULL，取值前必须判空（本工程做了，很好）；③必须 cJSON_Delete 释放，否则每次下行指令都漏一块堆内存——本工程在末尾调用了，正确；④cJSON 大量用 malloc，在 20KB RAM 的 MCU 上是主要内存风险，可考虑换 jsmn 之类的零分配解析器。这个「换零分配解析器」的建议非常加分。

I · 系统设计 / 综合

I1画一下整个系统的数据流？必问

要点（照架构图讲）：
采集路径：TIM1 每 500ms 置 TIM1_Timeout_Flag → ModbusTask 里 Modbus_Parse() 检测到标志 → 读 AHT20(温湿度) / INA226(电压电流功率) / ADC(电位器+CPU温度) → 写入 REG_HOLD_BUF[1..7]。
输出路径（三路并发）：① Modbus 主站读 03 功能码 → FreeModbus 回调从 REG_HOLD_BUF 取值回帧；② MQTTTask 每 2s 把 REG_HOLD_BUF[1..7] 拼成 JSON 经 AT 指令上行；③ CANopen 把数据映射到 OD 0x2000，通过 TPDO/SDO 发到 CAN 总线。
控制路径（反向）：① Modbus 06/10 写 REG_HOLD_BUF[0] → Modbus_Parse() 按位驱动 LED/蜂鸣器/继电器；② MQTT 下行 JSON → MQTT_Parse_JsonData() 解析 LED1/LED2/BEEP/RELAY → 同样写 REG_HOLD_BUF[0]；③ CANopen SDO/RPDO 写入 → OD 回调 → 同步控制。
一句话：REG_HOLD_BUF[] 是全局数据总线，三条协议都是它的「视图」。

I2三条协议共享一份数据，怎么保证一致性？现在有什么问题？必问

要点：见 E5。补充：①REG_HOLD_BUF[0] 的位操作用「读-改-写」，两个协议同时写会丢位，应先读快照再原子提交；②上报的 7 个寄存器不是同一时刻的快照，可能撕裂，应该「加锁拷一份到临时数组再上报」；③CANopen 侧 DeviceInfo_* 与 REG_HOLD_BUF 之间还需要一层同步（本工程靠 OD 回调），要确认回调是原子更新的。

I320KB RAM / 64KB Flash 你怎么做取舍？加分

要点：①RAM：能用静态就不用动态，malloc 尽量只在初始化阶段；缓冲区分配合理论峰值；FreeRTOS 堆压到 3KB；②Flash：CanFestival + FreeModbus + cJSON 三个库都很大，可关掉不用的功能码、关掉调试打印、用 -Os、把常量字符串放 const 进 Flash；③外设缓冲用 DMA 直传减少 RAM 中转。

I4项目名带 OTA，你会怎么设计 OTA 升级？加分

要点：F103C8 只有 64KB Flash，做 A/B 双分区很紧张，更现实的是 Bootloader + 单 App 分区：①Bootloader 占 8~12KB，App 从 0x08003000 起；②升级流程：云端下发固件（分片，经 MQTT/CANopen SDO/Modbus 均可）→ 写入 Flash 暂存区或直接擦写 App 区 → 校验（CRC32 / MD5）→ 置升级标志到 EEPROM 或备份寄存器 → 复位 → Bootloader 检查标志、校验通过则跳转新 App，失败则回滚；③要点：断点续传、掉电保护、版本号防回滚、跳转前关中断、重设向量表 SCB->VTOR、__set_MSP()。这个回答能直接体现工程完整度。

I5现场出现 HardFault 你怎么定位？必问

要点：本工程 HardFault_Handler 是死循环，没有任何信息，这是必须改进的地方。标准做法：①在 Handler 里读栈帧（MSP/PSP 自动压栈的 8 个寄存器），取出 PC 值，配合 .map 文件或 Keil 反汇编定位到出错行；②读 CFSR（SCB->CFSR）判断是总线错误/内存管理错误/用法错误；③读 BFAR/MMFAR 拿到非法访问地址；④常见原因：空指针、数组越界、栈溢出、未对齐访问、在中断里调了不可重入函数、任务栈太小。⑤Keil 可以开 HardFault 断点或用 Fault Report 脚本自动解栈。

I6这个项目你觉得最大的技术难点是什么？必问

要点（按含金量排序，挑 1~2 个讲）：①CanFestival 的移植——需要自己实现 canSend/canDispatch/setTimer/getElapsedTime 四个硬件接口，还要用 TIM2 做出 1us 精度的软件定时器，且 MS_TO_TIMEVAL 的换算必须和预分频严格对应；②不定长帧接收——串口 IDLE 中断 + DMA 循环 + 半满/全满回调 + 环形队列 + TIM4 二次判帧，四层配合才稳定，中间任何一环出错都会丢包；③三协议共存的实时性——三个任务抢 CPU，还要保证 CANopen 的定时不能被拖慢。

J · 工程化 / 工具链

J1CubeMX 生成的代码和你写的代码怎么隔离？重新生成会覆盖吗？重点

要点：所有手写代码必须放在 /* USER CODE BEGIN xxx */ 与 /* USER CODE END xxx */ 之间，CubeMX 重新生成时只保留这对标记内的内容。注意：OD/TestSlave.c 是 gen_cfile.py 生成的、Drivers/ 是 HAL 官方库、Middlewares/ 是 FreeRTOS 源码，这三处都不应该手改。目录结构上 Core/(应用+配置) / Drivers/(HAL) / Middlewares/(RTOS) / OD/(对象字典) / Canfestival/ / FreeModbus/ 分层清晰，是加分项。

J2Keil 里 printf 重定向到串口为什么要勾 MicroLIB？重点

J3你平时怎么调试这类多协议嵌入式系统？重点

问题位置与现象改进方案（背下来）
中断里阻塞打印
最高危		 stm32f1xx_it.c 的 USER_UART_IRQHandler() 里 printf("FIFO Full\n")；HAL_GPIO_EXTI_Callback 里 6 处 printf。fputc 是 HAL_MAX_DELAY 阻塞发送。 中断里只置标志/入队，打印移到任务；或改成环形缓冲 + DMA 异步发送；至少把 HAL_MAX_DELAY 换成有限超时。
共享数据无保护
必问		 REG_HOLD_BUF[] 被 ModbusTask / MQTTTask / CAN 中断读写，无任何锁或临界区；&= ~mask 是读-改-写。 加 taskENTER_CRITICAL() 保护短临界区；或引入互斥量；上报时先加锁拷贝快照再发送。
DMA 长度类型溢出
加分		 uint8_t Length = DMA_BUF_SIZE - __HAL_DMA_GET_COUNTER()，DMA_BUF_SIZE=256，结果为 256 时截断为 0。 类型改为 uint16_t / uint32_t；RX1_Offset/RX3_Offset 同步改宽。
任务栈偏小
重点		 3 个任务栈均为 128 words = 512B，任务内有 sprintf、cJSON_Parse、多层函数调用。 提到 ≥1KB；打开 configCHECK_FOR_STACK_OVERFLOW，用 uxTaskGetStackHighWaterMark() 实测后定值。
任务里 HAL_Delay 长忙等
重点		 Test_WIFI4G_CMD_Status() 内部 HAL_Delay(1)，MQTT 连网超时最长 200 秒，CPU 全程空转。 改成 osDelay(1) 释放 CPU；更好的做法是用信号量/事件组等待中断置位，而不是轮询标志。
堆偏小
加分		 configTOTAL_HEAP_SIZE = 3072，3 任务栈+TCB 已占约 1.9KB。 加大堆或全面静态分配；打开 configUSE_MALLOC_FAILED_HOOK 捕获分配失败。
CAN 中断里跑协议栈
重点		 HAL_CAN_RxFifo0MsgPendingCallback 里直接 canDispatch()，可能反向调 canSend。 ISR 只入队 + 释放信号量，dispatch 放到 CANopen 任务上下文；或至少确认协议栈可重入性。
CAN 未开自动恢复
重点		 AutoBusOff = DISABLE、AutoRetransmission = DISABLE。 生产环境建议都 ENABLE，保证 Bus-Off 自恢复、丢帧自动重发。
错误标志清除写错
加分		 huart->ErrorCode &= HAL_UART_ERROR_FE; 注释说「清除」，实际是「保留该位」。 应为 &= ~HAL_UART_ERROR_FE。
while 当 if 用
加分		 canSend() 里 while(...!=HAL_OK){ return 0; }，循环体无条件 return，最多执行一次。 改成 if，或真正实现「等邮箱空闲重试」。
HardFault 无信息
必问		 HardFault_Handler 只有 while(1)，现场无法定位。 实现栈帧解析打印 PC/LR/CFSR，或加 Keil Fault Report；开独立看门狗兜底。
三任务同优先级
重点		 全部 osPriorityNormal，靠时间片轮转。 按实时性分级：CANopen > Modbus > MQTT；或改事件驱动降低轮询开销。
TIM3 空转
基础		 TIM3 初始化了（5ms）但中断里没有任何业务，白占一个外设和中断。 确认需求后删除，或用于看门狗喂狗/心跳 LED。
回答这类问题的正确姿势 不要辩解「能跑就行」。标准话术是：「这里确实有隐患，我当时是按 XXX 场景做的简化；如果上生产我会改成 YYY，原因是 ZZZ。」 承认 + 给方案 + 说清权衡，比强行辩护得分高得多。

5可以主动抛出的加分话题

面试尾声，主动讲这些能把「做完了」升级成「做好了」：

架构层面

  • 把 REG_HOLD_BUF 抽象成统一的「数据模型层」，三个协议只做适配器，新增协议（如 BACnet、EtherCAT）不改业务代码
  • 模组驱动抽象成函数指针接口，WiFi/4G/以太网可运行时切换，替代 #if 宏
  • 事件驱动替代轮询：用队列 + 信号量替代 osDelay(10) 死等

可靠性层面

  • 独立看门狗 IWDG + 各任务喂狗上报，单任务卡死可复位
  • 统一错误处理：EMCY（CANopen）+ 异常寄存器（Modbus）+ 告警上报（MQTT）三路故障通知
  • 参数持久化：从机地址、CANopen NodeID、上报周期都存 EEPROM/Flash 参数区，带 CRC 校验
  • 断网缓存：MQTT 断线时数据存本地环形缓冲，恢复后补传

性能层面

  • CANopen PDO 用事件触发 + 抑制时间，替代周期发送，降低总线负载
  • 串口发送改 DMA + 空闲中断，去掉逐字节阻塞
  • 用 uxTaskGetStackHighWaterMark 和 vTaskGetRunTimeStats 量化优化，而不是拍脑袋

工程化层面

  • 引入 Git 分支策略 + .ioc 与手写代码分离，避免 CubeMX 覆盖
  • 写主机端测试脚本（Python + pymodbus + python-can + paho-mqtt）做自动化回归
  • 把 OD/*.od 的生成流程写进构建脚本，改 OD 自动重新生成 TestSlave.c
